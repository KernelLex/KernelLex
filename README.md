### [TrueCommit](https://github.com/KernelLex/track-03)
[![Live](https://img.shields.io/badge/Live_app-000000?style=flat-square&logo=vercel&logoColor=white)](https://truecommit-tawny.vercel.app/)
[![Evidence](https://img.shields.io/badge/Real_money_batch-0E7490?style=flat-square&logo=razorpay&logoColor=white)](https://github.com/KernelLex/track-03/blob/master/docs/evidence/REAL_BATCH.md)
[![Results](https://img.shields.io/badge/Results-5B21B6?style=flat-square&logo=databricks&logoColor=white)](https://github.com/KernelLex/track-03/blob/master/docs/RESULTS.md)

A bounded autonomous agent for Indian B2B and subscription revenue recovery, built for the Razorpay AI Buildathon 2026. Seven agents run the pipeline and none of them can call another: they coordinate only through an append-only, hash-chained ledger. The model may read what a debtor actually wrote and propose a typed candidate action, but it may never spend. Amount, date, state transition and gate verdict are all deterministic code. One gate of 20 rules decides whether anything is allowed to happen, 7 of them regulatory (RBI, TRAI, MSMED) and 13 filed apart as stopping rules, because calling company policy regulation would overstate it. Each rule is written twice and a 5,000 case property test asserts the two implementations agree, and a refusal is logged as a decision rather than as silence. Ten agent-chosen actions ran with dry run off: five created real Razorpay invoices, all five were paid, and ₹215,867 was captured, with every status fetched back from Razorpay at report time instead of read out of its own ledger. Any dispute, or a debtor in a low credibility band, holds the payment links for human approval. The subscription half uses no model at all: it reads the mandate book and finds debits that cannot succeed before they fail. Every inbound webhook is signature verified before anything reads it, under Razorpay's own scheme, Telegram's secret token and Twilio's HMAC-SHA1 over URL and sorted params.

### [Throttle](https://github.com/KernelLex/throttle)
[![Live](https://img.shields.io/badge/Live_dashboard-000000?style=flat-square&logo=vercel&logoColor=white)](https://throttle-delta.vercel.app)
[![Tour](https://img.shields.io/badge/Watch_the_tour-B45309?style=flat-square&logo=youtube&logoColor=white)](https://github.com/KernelLex/throttle/blob/main/brag-output/brag.mp4)

A production email job scheduler. It takes campaigns over an API, spreads them across multiple senders under per-sender hourly limits, sends over SMTP, and survives a restart without losing or duplicating a single send. Two decisions carry most of the design. Postgres is the only source of truth and rebuilds Redis on every boot, so a cold start or a wiped Redis costs nothing and an overdue backlog is re-spaced rather than dropped. And one function, `planSchedule()`, is imported by the browser and the server both, so the forecast a user sees is produced by the same code that does the scheduling. Rate limiting is a Lua script in Redis, so a send slot is granted atomically across workers, and hitting a limit moves the job to the next window without consuming a retry attempt, because throttling is not failure. Workers claim a job with a conditional update that returns rows, so two of them can never send the same email. When Render silently blocked outbound SMTP on free instances, the circuit breaker opened after five consecutive failures, rerouted traffic and deferred the queue instead of discarding it, which exercised the failure path against a real outage rather than a staged one. Rate-limit alerts go to Slack, and search runs on Elasticsearch with a labelled Postgres fallback when no cluster is configured.

### [Promise Keeper](https://github.com/KernelLex/TrueCommit)

The earlier entry in the same Razorpay track, and the one that argues the thesis with numbers. ₹8.1 lakh crore of Indian MSME money sits in delayed payments, and roughly 70% of online carts are abandoned before checkout. Current tooling treats both the same way: a reminder that asks the customer to decide again later, at a colder moment than the one where they said yes. Promise Keeper converts stated intent into a self-executing instrument on Razorpay's rails at the moment of commitment, and falls back to a message only when there is no commitment to capture. The instruments already exist; the judgment about which one to deploy, to whom and when, read out of unstructured text, is what this builds. It keeps measured results and simulated results strictly apart and never passes one off as the other: promise extraction holds 88.6% on qwen2.5:7b against a 97.7% in-sample ceiling for the hand-written heuristic, triage runs 91.7% on the invoices that actually carry a message thread, and output is byte identical across independent runs at seed 42. The three-arm recovery comparison is labelled simulated throughout and reports the uncomfortable result rather than the flattering one: an unbounded reminder baseline recovers more nominal rupees, while this system needs under half the contact attempts per recovery because it respects a per-debtor weekly touch cap and freezes autonomous action on every invoice of a debtor who has disputed one. Headline figures are re-run across a 10% to 60% mandate-acceptance band instead of resting on one assumed rate. 721 tests, offline by default.

### [HRMS](https://github.com/KernelLex/hrms) · *team project*
[![Live](https://img.shields.io/badge/Live_demo-000000?style=flat-square&logo=vercel&logoColor=white)](https://hrms-amogh24.vercel.app)

The HR module of an ERP, built for Indian companies: payroll, leave, hiring, performance and income tax. Every fact is dated, so anyone's pay, position or address can be read as it stood on any past date, and a change applies from the day it takes effect without destroying what came before. The modules feed each other rather than sitting side by side. Converting a candidate creates the employee, job, working time and pay in one step, so there is never a half-made record and nothing is retyped. An approved day of unpaid leave becomes a deduction in the next payroll run. An increment agreed in an appraisal becomes next month's basic pay in time for payroll to read it. Every run adds to the record Form 16 is built from, so the tax return and what was actually deducted cannot disagree. A bank-detail change needs proof and two approvers, and whoever decides the first step can never decide the second. Five seeded accounts on the live demo show the same system as HR, a manager, an employee, a recruiter and finance each see it, and WCAG 2.1 AA is checked automatically on every change.

### [Trading Strategy Engine](https://github.com/KernelLex/trading-engine)

A quantitative research platform that runs the whole loop, from raw market data to an explanation of why a strategy performed the way it did. It ingests prices, news, FRED macro series and optional Reddit discussion, scores sentiment with FinBERT and aggregates it by sector, then has an LLM agent read the resulting signal summary and propose trading hypotheses. Surviving hypotheses are ranked, filtered and converted into structured, validated strategies, backtested through a signal interpreter and portfolio simulator, and finally attributed back to the individual signals with SHAP, so each result carries a written account of what drove it. Twelve DuckDB tables are created automatically and a React dashboard sits on top.
